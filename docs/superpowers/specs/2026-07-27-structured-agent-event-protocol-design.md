# Structured Agent Event Protocol Design

## Status

Approved for implementation on 2026-07-27.

## Context

FFCode already separates the Agent loop from terminal rendering through `AgentEvent`, but those events are internal Go values. Automated callers currently infer completion by parsing rendered terminal text such as `done: end_turn`. Terminal text is not a protocol: it contains ANSI control sequences, Markdown, translated status messages, arbitrary model text, and output chunks that may split markers.

The structured protocol is a general Agent capability. SWE-bench exposed the failure mode and will be one regression data source, but the design must support any interactive or automated caller.

## Goals

- Give every Agent turn a stable, versioned, machine-readable event stream.
- Preserve the existing terminal UI as the default behavior.
- Make turn completion explicit and independent of rendered text.
- Distinguish successful, incomplete, failed, and cancelled turns.
- Preserve streaming text, thinking, tool lifecycle, result, and usage events.
- Guarantee exactly one terminal event for every started turn.

## Non-Goals

- Provider-specific retry and backoff behavior.
- Continuing a response after `max_tokens`.
- Deadline and convergence policies.
- A remote network API.
- Slash commands in JSONL mode.

## CLI Contract

FFCode accepts a new option:

```text
--output-format text|jsonl
```

`text` is the default and preserves the existing terminal experience. In `jsonl` mode:

- stdin is line-oriented; each non-empty line starts one user turn;
- stdout contains JSONL events only;
- stderr contains startup and configuration diagnostics;
- no welcome text, prompt, Markdown rendering, status animation, or ANSI output is written to stdout;
- EOF exits successfully after any active turn finishes;
- slash commands are not interpreted in protocol version 1.

Unknown output formats are rejected as command-line usage errors.

## Internal Event Model

The Agent owns lifecycle semantics. UI packages render events but do not infer whether a turn succeeded.

A new `TurnEndEvent` replaces successful `DoneEvent` and terminal uses of `ErrorEvent`:

```go
type TurnStatus string

const (
    TurnCompleted  TurnStatus = "completed"
    TurnIncomplete TurnStatus = "incomplete"
    TurnFailed     TurnStatus = "failed"
    TurnCancelled  TurnStatus = "cancelled"
)

type StopReason string

const (
    StopEndTurn          StopReason = "end_turn"
    StopMaxTokens        StopReason = "max_tokens"
    StopCancelled        StopReason = "cancelled"
    StopDeadlineExceeded StopReason = "deadline_exceeded"
    StopProviderError    StopReason = "provider_error"
    StopAgentError       StopReason = "agent_error"
)

type TurnEndEvent struct {
    Status         TurnStatus
    StopReason     StopReason
    ProviderReason string
    Usage          llm.UsageInfo
    Err            error
}
```

`ProviderReason` preserves the raw provider value without making it part of the stable internal enum.

### Stop Reason Mapping

| Provider reason or error | Status | Stable reason |
|---|---|---|
| `end_turn`, `stop`, `stop_sequence` | `completed` | `end_turn` |
| `max_tokens`, `length` | `incomplete` | `max_tokens` |
| empty or unknown final reason | `incomplete` | `agent_error` |
| `context.Canceled` | `cancelled` | `cancelled` |
| `context.DeadlineExceeded` | `failed` | `deadline_exceeded` |
| other stream, context, validation, or loop error | `failed` | `agent_error` |

Provider errors remain `agent_error` until the typed Provider error work is implemented. That later work may map them to `provider_error` without changing the wire schema.

The Agent emits exactly one `TurnEndEvent` before closing the event channel. Tool failures remain `ToolResultEvent{IsError: true}` and do not terminate a turn by themselves.

## Wire Protocol

Every output line is one JSON object with a versioned envelope:

```json
{
  "version": 1,
  "sequence": 3,
  "type": "turn_finished",
  "session_id": "session-id",
  "turn_id": "turn-1",
  "data": {
    "status": "completed",
    "stop_reason": "end_turn",
    "provider_reason": "end_turn",
    "usage": {
      "input_tokens": 100,
      "output_tokens": 20,
      "total_tokens": 120,
      "cache_read_tokens": 0,
      "cache_creation_tokens": 0
    }
  }
}
```

The envelope fields are stable within protocol version 1. `sequence` starts at 1 for each process and increases for every emitted wire event. `turn_id` is generated by the JSONL runner and is unique within the process.

Version 1 event types:

- `turn_started`
- `thinking_started`
- `thinking_delta`
- `text_delta`
- `tool_call_started`
- `tool_call_delta`
- `tool_call_completed`
- `tool_execution_started`
- `tool_result`
- `turn_finished`

Each event has a type-specific `data` object. Error information is only present on failed, incomplete, or cancelled `turn_finished` events and exposes a message, not Go implementation details.

## Components

### Agent Lifecycle

`internal/agent` classifies stop reasons and converts every exit path into one `TurnEndEvent`. A single helper constructs terminal events so validation, context building, streaming, cancellation, and iteration exhaustion follow the same rules.

### Protocol Encoder

A new `internal/protocol` package maps `AgentEvent` values into the version 1 envelope and encodes one JSON object per line. The encoder does not own sessions, read stdin, render ANSI, or execute the Agent.

### JSONL Runner

A new `internal/ui/jsonl` package owns line-oriented machine interaction. For each non-empty input line it:

1. stores the user message;
2. emits `turn_started`;
3. runs the Agent;
4. encodes every Agent event;
5. waits for the terminal event before reading the next line.

The existing terminal package remains responsible for human interaction. It renders the same `TurnEndEvent` semantics without parsing protocol JSON.

### Application Assembly

`internal/app` parses `--output-format`, builds one runtime, and selects either the terminal runner or JSONL runner. Startup failures continue to use stderr and process exit codes because no turn has started yet.

## Error Handling

- JSON encoding or stdout write failure stops JSONL mode and returns a non-zero process exit code.
- A failed Agent turn emits `turn_finished` with `status=failed`; the JSONL process remains available for the next input line.
- A cancelled turn emits `status=cancelled` when the cancellation reaches the Agent.
- Channel closure without a terminal event is treated as an Agent invariant violation and produces a synthetic failed `turn_finished` event.
- Error messages are strings. Stack traces and wrapped internal types are not part of protocol version 1.

## Testing

Implementation follows TDD and covers:

- normal stop reasons map to `completed`;
- token-limit stop reasons map to `incomplete`;
- cancellation, deadline, validation, stream, and iteration errors each emit one terminal event;
- JSON encoding emits valid newline-delimited objects without ANSI bytes;
- all Agent event types map to the expected version 1 event name and payload;
- sequence values are monotonic and turn IDs remain stable within a turn;
- `--output-format` defaults to `text`, accepts `jsonl`, and rejects unknown values;
- terminal rendering continues to handle completed and failed turns;
- JSONL stdout contains no welcome text or terminal status output.

After focused tests pass, run `gofmt`, `go test ./...`, and `go test -race` for the Agent, protocol, and UI packages affected by lifecycle or concurrent event handling.

## Compatibility

- Existing users receive the same text UI unless they request JSONL.
- Existing session and transcript formats do not change.
- Protocol evolution uses the top-level `version`; incompatible field changes require a new version.
- Adding optional fields or new event types may remain within version 1 when existing event meanings do not change.
